# 카카오맵 기반 최적 배송코스 도출 – 구현계획 & 설계

> S-FOOD TMS · Route Optimizer
> 단순 순회(TSP)부터 납품처별 제약을 반영한 다차량 배차(VRPTW)까지 옵션으로 단계 확장

---

## 1. 목표와 범위

| 구분 | 내용 |
|---|---|
| 목표 | 차고지에서 출발해 N개 납품처를 도는 **최소 비용 배송코스**를 도출 |
| 확장축 | ① 차량 대수(1대 TSP → M대 VRP) ② 제약조건(무제약 → 용량/시간창/순번/운행한도) |
| 거리 기준 | **카카오모빌리티 길찾기 API 실제 도로거리/소요시간** (직선거리는 폴백 전용) |
| 산출물 | 단일 HTML 앱 (`index.html`) + CORS 프록시 (`tools/kakao-proxy.mjs`) |

### 문제 유형 매핑

```
차량 1대 + 제약 없음                        → TSP        (순회 외판원)
차량 1대 + 시간창                           → TSPTW
차량 M대 + 용량                             → CVRP
차량 M대 + 용량 + 시간창 + 하역 + 운행한도  → CVRPTW  ← 최종 목표
                                   + 고정순번/우선순위 → CVRPTW + Precedence
```

### 왜 프록시가 필요한가

카카오모빌리티 길찾기 API(`apis-navi.kakaomobility.com`)는 **서버 간 호출용**으로,
`Access-Control-Allow-Origin` 응답 헤더를 내려주지 않습니다. 따라서 브라우저에서
`fetch()`로 직접 호출하면 CORS 정책에 의해 차단됩니다.

동봉한 `tools/kakao-proxy.mjs`가 이를 해결하며, **부수 효과로 REST API 키가
브라우저에 노출되지 않습니다**(키는 프록시 프로세스의 환경변수에만 존재).
앱은 "직접 호출" 모드도 지원하지만, 사내 배포 시에는 프록시 사용을 권장합니다.

## 4. 거리행렬 구축 전략

N개 납품처 → (N+1)×(N+1) 행렬. 순진하게 하면 API 호출 N² 회.

| 단계 | 사용 API | 호출 수 | 비고 |
|---|---|---|---|
| ① 1:N 일괄 | `POST /v1/destinations/directions` | (N+1) × ⌈N/30⌉ | 목적지 최대 30개/요청 |
| ② 실패 보정 | `GET /v1/directions` | 실패 쌍 수 | `radius`(≤10km) 초과 쌍 |
| ③ 최종 폴백 | Haversine × 우회계수 | 0 | 추정치로 표시(UI 경고) |
| ④ 캐시 | localStorage | 0 | 좌표쌍 키, 재최적화 시 무호출 |

납품처 20곳 기준: **21회 호출**(①) + 소수 보정 → 실무 규모에서 충분히 빠름.
최종 확정 경로의 폴리라인만 `POST /v1/waypoints/directions`(경유지 30개)로 별도 조회.

## 5. 최적화 알고리즘

### 5.1 파이프라인

```
① 초기해   Clarke-Wright Savings (용량·시간창 인지)
              └ 병합 가능 여부를 제약 평가로 판정, 차량 대수까지 축약
② 개선     Simulated Annealing + 5종 근방 연산
              relocate · swap · 2-opt · or-opt(2~3연쇄) · 2-opt*(경로간 꼬리 교환)
③ 다듬기   Steepest-descent 지역탐색 (더 이상 개선 없을 때까지)
④ 복구     고정순번(first/last) 강제 재배치
⑤ 실경로   차량별 waypoints 길찾기 → 도로 폴리라인
```
전 과정은 `timeLimitMs` 예산 안에서 수행하며, 2,000회마다 이벤트루프에 양보해
**UI가 멈추지 않습니다**(진행률 표시).

### 5.2 비용 함수 — "제약을 옵션으로" 구현하는 핵심

모든 제약은 **미터 환산 페널티**로 단일 스칼라에 합산됩니다.
옵션 토글을 끄면 해당 항의 가중치가 0이 되어, 같은 엔진이 TSP부터 CVRPTW까지 커버합니다.

```
cost(해) = Σ_경로 [ base + penalty ]

base    = objective=='distance' ? 총거리(m)
                                : 총소요(초) × 10        // 1초 ≒ 10m 등가

penalty = 3,000 × 시간창 지각(분)          ← useTimeWindow
        + 200,000 × (초과적재 / 적재한도)   ← useCapacity
        + 3,000 × 운행시간 초과(분)        ← useMaxDuration
        + 3,000 × 운행종료 초과(분)
        + 200,000 × 고정순번 위반 건        ← useFixedOrder
        +  20,000 × 우선순위 역전 쌍
        + 2,000,000 × 미배정 납품처
```

`제약 모드 = hard`이면 위반을 만드는 근방 이동을 아예 기각하고,
`soft`면 페널티만 물려 탐색 공간을 넓힙니다(막다른 골목 회피).

### 5.3 스케줄 계산 (시간창·하역·대기)

```
t ← 차량 운행시작
각 방문 k:
    t += 이동시간(이전, k)
    도착 = t
    if 도착 < 납품가능 시작 → 대기 (t ← 시작)     // 대기 허용 옵션
    if t > 납품가능 종료   → 지각 위반 기록
    t += 하역시간(k)
복귀: t += 이동시간(마지막, 차고지)
```
**출발시각 자동 보정**: 첫 방문에서 대기가 발생하면 그만큼 출발을 늦춥니다.
이후 일정은 완전히 동일하면서 총 구속시간만 줄어드는, 손해 없는 개선입니다.

## 6. 시각화 설계

### 6.1 차량 식별 — 4색 × 3패턴 복합 인코딩

경로 색은 색각 이상 검증(OKLab ΔE, all-pairs)을 **통과한 4색만** 사용합니다.

| 슬롯 | 색상 | HEX |
|---|---|---|
| 1 | blue | `#2a78d6` |
| 2 | orange | `#eb6834` |
| 3 | aqua | `#1baf7a` |
| 4 | violet | `#4a3aa7` |

> 5색 이상은 all-pairs 검증에서 실패(주황↔노랑 정상시야 ΔE 13.7 < 15)하므로
> 색상을 늘리지 않고 **선 패턴(실선/파선/점선)** 을 곱해 12대까지 구분합니다.
> 여기에 마커의 `차량-순번` 텍스트 배지, 범례, 결과 테이블이 항상 함께 제공되어
> 색상 단독으로 의미를 전달하지 않습니다.

경로 폴리라인은 **흰색 케이싱(외곽선)** 위에 본선을 얹어, 지도 타일 색과
무관하게 대비를 확보합니다.

### 6.2 배송 타임라인

차량별 1행 간트 차트(SVG). 이동/대기/하역을 구분하고, 납품 가능 시간창을
배경 밴드로 깔아 **위반이 눈에 바로 보이도록** 합니다. 호버 툴팁 제공.

### 6.3 테마

지도 타일이 밝은 면이므로 **라이트 테마 단일**로 확정했습니다. 차량 색상이
지도와 타임라인에서 동일하게 유지되어야 하는데, 다크 팔레트로 재계산하면
동일 차량이 두 화면에서 다른 색이 되어 "색은 개체를 따른다" 원칙이 깨집니다.

## 8-2. 온도대 (냉장 · 냉동)

식품 물류에서는 한 납품처에 상온·냉장·냉동이 함께 나간다. 따라서 물량을 단일 수치가 아니라
**온도대별 벡터**로 잡았다.

```js
Stop.demand = {
  ambient: { w, v, b },   // 상온
  chilled: { w, v, b },   // 냉장
  frozen:  { w, v, b },   // 냉동
}
Vehicle.zones = {
  ambient: { allowed, capWeight, capVolume, capBoxes },  // allowed=false 면 적재 불가
  ...
}
Vehicle.compartments  // true = 칸별 한도 적용(칸막이차), false = 차량 총량만
```

### 제약 → 페널티 매핑

| 제약 | 판정 | 페널티(미터 환산) |
|---|---|---|
| 적재 호환성 | 차량이 허용하지 않는 온도대를 실음 | 500,000 (혼적 금지 시 ×4) |
| 칸별 한도 | 칸막이차의 칸 적재량 초과 | 300,000 + 초과비율 × 200,000 |
| 배차 분리 | 한 경로가 여러 온도대를 담당 | 30,000 × (온도대 수 − 1) |
| 냉동 우선 | 냉동 납품처가 비냉동 뒤로 밀림 | 800 × 역전 쌍 수 |

냉동 우선은 역전 **쌍**으로 세면 O(n²)로 커져 시간창 지각(3,000/분)이나 적재 호환성을
눌러버린다. 탐색 기울기는 쌍 단위가 좋으므로 세는 방식은 유지하되 단가를 800으로 낮춰
균형을 맞췄다. 위반 표시에는 "밀린 냉동 납품처 수"를 함께 보여 해석 가능하게 했다.

### 하역시간

온도대가 여러 개면 분리 하역으로 시간이 더 걸린다.

```
실제 하역시간 = 입력 하역시간 + 가산분 × (온도대 수 − 1)
```

CSV 내보내기는 `하역(분)`에 **입력값**을, `실하역(분)`에 가산이 반영된 값을 따로 낸다.
그렇지 않으면 내보내기→가져오기를 반복할 때마다 하역시간이 누적되어 부풀어 오른다.

### 하위 호환

온도대 정보가 없는 기존 데이터(구버전 localStorage, 단일 물량 CSV)는 전부 **상온**으로
이관된다. 기본 차량의 상온칸 한도를 차량 총량과 같게 잡아, 예전에 가능하던 배차가 갑자기
위반으로 바뀌지 않도록 했다.

### 색 설계

"차가움"은 순서형 척도이므로 단색(파랑) 램프를 **밝음 → 어두움**으로 쓴다.
상온은 냉기가 0이라 중립 회색이다. 지도의 차량 식별색(범주형 4색)과는 쓰이는 맥락이 달라
충돌하지 않으며, 칩에는 **항상 아이콘과 라벨이 함께** 붙어 색만으로 의미를 전달하지 않는다.

## 9. 알려진 제약

1. **카카오맵 JS SDK는 도메인 등록이 필요합니다.** `file://`로 열면 동작하지
   않으므로 로컬 웹서버(예: `npx serve`)로 띄우고 해당 도메인을 카카오
   디벨로퍼스에 등록해야 합니다.
2. `POST /v1/destinations/directions`의 `radius`는 최대 10km입니다. 그 밖의
   쌍은 개별 길찾기로 보정하며, 그마저 실패하면 직선거리 추정치로 대체하고
   UI에 **추정 구간 수를 명시**합니다.
3. 최적화는 휴리스틱이므로 **전역 최적해를 보장하지 않습니다.** 탐색 시간을
   늘리면 해 품질이 올라갑니다(옵션에서 조절).
4. 차량 12대, 납품처 200곳 내외를 실용 상한으로 설계했습니다.
